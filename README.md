# AgTech Fields GIS — Веб-застосунок для управління полями

Сучасний клієнтський веб-застосунок для управління сільськогосподарськими полями та моніторинговими точками на інтерактивній карті Leaflet. Розроблено відповідно до технічного завдання для Frontend Engineer.

---

## 🚀 Швидкий старт та інструкція запуску

### Вимоги:
* **Node.js:** v18+ (рекомендовано v20 або вище)
* **npm:** v9+

### Встановлення та запуск:
```bash
# 1. Клонувати репозиторій (або перейти в папку проєкту)
cd tst-tsk

# 2. Встановити залежності
npm install

# 3. Запустити локальний сервер розробки
npm run dev
```

Після запуску відкрийте браузер за посиланням: `http://localhost:5173`

### Збірка для продакшну:
```bash
npm run build
npm run preview
```

## 🛠 Використані технології

* **Core & Build:**
  * **React 18+ & TypeScript** — строгий режим типізації (`strict: true`, жодного `any`), компонентний підхід.
  * **Vite** — надшвидка збірка та миттєвий HMR.
* **Картографія та GIS:**
  * **Leaflet & React-Leaflet** — інтерактивна робота з картою, рендеринг шарів GeoJSON, керування зумом і фокусуванням (`fitBounds`, `flyTo`).
  * **@turf/boolean-point-in-polygon & @turf/helpers** — алгоритмічна перевірка знаходження точки строго всередині контуру обраного поля (Ray-Casting під капотом).
  * **mgrs** — перерахунок координат WGS 84 у військову систему координат MGRS прямо на клієнті.
* **Управління станом:**
  * **Zustand** — легковагий (~1 KB) стейт-менеджер із селективними підписками. Запобігає каскадним ререндерам важкого дерева DOM карти.
  * **LocalStorage persistence** — автоматичне збереження створених точок між сесіями.
* **Стилізація та UI/UX:**
  * **Tailwind CSS v4** — сучасна утилітарна стилізація, адаптивність.
  * **lucide-react** — векторні іконки під кожен тип моніторингу та елементи інтерфейсу.

## 🏛 Прийняті архітектурні рішення

1. **Розмежування осей координат (`[lat, lng]` vs `[lng, lat]`):**
   * *Проблема:* Leaflet працює з форматом `[latitude, longitude]`, тоді як стандарт GeoJSON (RFC 7946), Turf.js та бібліотека MGRS строго вимагають `[longitude, latitude]`.
   * *Рішення:* Всі операції конвертації ізольовані в модулі `src/utils/geo.ts`. Це гарантує математичну точність і унеможливлює баги зі зміщенням точок в іншу півкулю.

2. **Zustand замість Redux Toolkit або Context API:**
   * *Context API* викликає повторний рендеринг усього дерева компонентів при кожній зміні пошукового запиту або фільтра.
   * *Redux Toolkit* є надлишковим за обсягом коду для клієнтського MVP.
   * *Zustand* забезпечує ізольовані оновлення (мапа підписана лише на зміну фокусу та список точок, сайдбар — на фільтри та пошук).

3. **Векторні SVG-маркери (`L.divIcon`):**
   * Замість стандартних картинок Leaflet (`marker-icon.png`), які часто дають помилку 404 у збірках Vite, використані динамічні `L.divIcon` з інлайн SVG та колірною диференціацією під 4 типи моніторингу:
     * 🧪 **Проба ґрунту** (Amber)
     * 🐛 **Шкідники** (Red)
     * 🍃 **Хвороби рослин** (Orange)
     * 📍 **Інше** (Blue)

4. **Адаптивність (Desktop + Tablet / Mobile):**
   * На екранах **≥ 1024px** інтерфейс організовано у два паралельних блоки (сайдбар зліва, карта на всю ширину справа).
   * На планшетах та смартфонах (**< 1024px**) передбачено нижній плаваючий перемикач вкладок («Карта» ↔ «Поля та Точки»), що забезпечує зручність роботи однією рукою.
   * Додано автовиклик `map.invalidateSize()`, що повністю виключає появу «сірих тайлів» при ресайзі вікна.

## 💡 Що б ви додали, якби мали більше часу?

1. **Кластеризація маркерів:**
   Підключення `leaflet.markercluster` для випадків, коли на одному полі зосереджено 500+ точок замірів.
2. **Експорт та імпорт даних:**
   Експорт відфільтрованих точок у формати CSV / GeoJSON / Shapefile для передачі агрономам або в бортові комп'ютери техніки.
3. **Вимірювання та аналітика:**
   Інструмент лінійки для вимірювання відстаней між точками та розрахунок середньої відстані обстеження.
4. **Офлайн-режим (PWA):**
   Кешування тайлів карти (Tile Cache via IndexedDB / Service Worker) для польових робіт без стабільного інтернет-зв'язку.

## 📋 Обґрунтовані припущення (Assumptions)

Відповідно до вимог ТЗ, під час реалізації було прийнято такі інженерні рішення та припущення:
1. **Збереження даних (Клієнтський рівень):** Оскільки бекенд не передбачений ТЗ, для безперервності користувацького досвіду реалізовано персистентність через `localStorage`. При першому запуску застосунок ініціалізується якісними мок-даними з різними типами замірів, реальними координатами та прив'язкою до полів.
2. **Стандарти координат:** 
   - Візуалізація та зберігання полів відповідає стандарту RFC 7946 (GeoJSON: `[lng, lat]`).
   - Точки моніторингу зберігають координати WGS 84 (`lat`, `lng`) з точністю до 6 знаків (~10 см).
   - Військова сітка MGRS генерується з точністю 1 м (точність 5) та форматується зі стандартними пробілами між зонами для швидкого зчитування оператором в польових умовах.
3. **Поведінка кліків на карті:**
   - Клік по **неактивному** полю робить його активним та виконує плавний `fitBounds` камери.
   - Клік по **активному** полю миттєво відкриває форму додавання точки з предзаповненими WGS 84 та розрахованими MGRS координатами.
   - Клік **за межами** поля активує Toast-повідомлення з валідаційною помилкою про необхідність кліку в межах обраного контуру.
4. **Адаптивність (Tablet + Desktop):**
   - На десктопах (≥ 1024px) застосовується двопанельний режим для одночасного аналізу табличних даних і картографічного шару.
   - На планшетах та мобільних пристроях (< 1024px) використовується перемикач вкладок із синхронізацією: вибір точки або поля зі списку автоматично фокусує та перемикає екран на карту.

## 🎯 Підготовка до технічного інтерв'ю (FAQ до захисту)

* **Чому Zustand, а не Redux Toolkit / Context API?**
  * Context API викликає ререндеринг всього дерева компонентів мапи при зміні пошуку в сайдбарі.
  * Redux Toolkit додає 15+ КБ бойлерплейту, не надаючи переваг для даного розміру проєкту.
  * Zustand надає атомарні селектори (`useFieldStore((s) => s.activeFieldId)`), що гарантує 0 зайвих перемальовувань важких векторних шарів Leaflet.
* **Чому Turf.js (`@turf/boolean-point-in-polygon`)?**
  * Алгоритм Ray-Casting у Turf.js враховує конкейвні полігони (увігнуті контури полів), дірки (multipolygons) та крайові випадки вершин, що виключає геодезичні похибки самописних простих формул.
* **Чому SVG `L.divIcon` замість дефолтних PNG Leaflet?**
  * Дефолтні картинки Leaflet ламаються в бандлерах (Vite) через особливості резолву статичних шляхів.
  * `divIcon` дозволяє рендерити кастомні SVG-іконки з різними кольорами категорій, бордерами та CSS-анімаціями без додаткових мережевих запитів.
